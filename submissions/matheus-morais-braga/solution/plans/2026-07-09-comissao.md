# Comissão por profissional — quanto cada um ganha sobre o que atendeu

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.
> **Documento-pai:** `docs/plans/2026-07-05-roadmap-multinegocio.md` (iniciativa 9, Onda F, Release 4).

**Goal:** dar ao dono de salão/barbearia/clínica/estética o número que ele mais cobra e hoje calcula
na mão: **quanto pagar de comissão a cada profissional** por período. O operador define **regras de
comissão** por profissional (percentual **ou** valor fixo, geral do profissional **ou** por serviço),
e no **fechamento da comanda** o sistema **snapshota** a comissão de cada linha creditada ao
profissional que atendeu. Um **relatório por profissional/período** soma tudo. Nada muda para as
contas que não ligam comissão (nenhuma regra ⇒ comissão zero, invisível).

**Architecture:** o coração do cálculo é **puro** em `src/lib/commission.ts` (sem DB): dada a regra
aplicável e a linha da comanda (`unitPrice × qtd`), ele deriva os centavos de comissão — 100%
testável, mesmo padrão de `availability.ts`/`orderTotalCents`. Um serviço `commission.service`
gerencia as **`CommissionRule`** (CRUD + validação). No **fechamento** (`closeOrder`), dentro da
**mesma transação** que já numera o cupom, baixa estoque e grava os tenders, resolvemos o profissional
creditado (explícito no fechamento **ou** derivado do **agendamento ligado** à comanda), carregamos as
regras dele e **snapshotamos** `OrderItem.professionalId` + `OrderItem.commissionCents` por linha. O
**relatório** (`commissionByProfessional`) é um `groupBy` sobre `OrderItem` das comandas `FECHADA` do
período — reusa o filtro que os outros relatórios de venda já usam. Estorno (`CANCELADA`) some do
relatório de graça (o filtro é `status=FECHADA`); reabertura **limpa** o snapshot p/ recalcular no
próximo fechamento.

**Tech Stack:** Prisma · Postgres (Supabase) · Zod · Vitest · Next.js (App Router) · TailwindCSS
(tokens/CSS vars — nunca hex [[design-tokens-dark-theme]]).

**Decisões travadas (produto):**
- **Comissão é SNAPSHOT no fechamento**, nunca derivada em tempo de leitura. O total da comanda é
  derivado (`orderTotalCents`), mas a comissão precisa sobreviver a mudança de regra/preço/exclusão
  do agendamento — igual `nameSnapshot`/`durationMinutes`/`unitPriceCents` já fazem. Mudar a regra
  **não** reprecifica comandas antigas.
- **Base da comissão = total BRUTO da linha** (`unitPriceCents × quantity`). Desconto/acréscimo/
  gorjeta são **de comanda** (difíceis de ratear por linha e a gorjeta em geral é 100% do
  profissional) — ficam **fora** da base no v1. Documentado; ratear desconto por linha é follow-up.
- **Um profissional creditado por comanda no v1** — o caso real (o barbeiro que cortou também vendeu
  a pomada). Todas as linhas recebem o **mesmo** `professionalId`; cada linha calcula sua comissão
  pela **sua** regra (serviços diferentes, percentuais diferentes). Comanda multi-profissional (dois
  profissionais no mesmo ticket) é follow-up — precisaria de atribuição por linha na UI.
- **Percentual em pontos-base** (`percentBps Int`, 4000 = 40,00%) — mantém a disciplina "dinheiro/
  proporção em `Int`, nunca float" ([[caixa-despesas-reposicionamento]]). A UI resolve `%` ↔ bps na
  borda (igual desconto resolve `%` → centavos).
- **Regra fixa é POR UNIDADE** (`fixedCents × quantity`) — R$10 por corte, 2 cortes na linha = R$20.
- **Exatamente um de `percentBps`/`fixedCents`** por regra (validação no serviço).
- **Precedência:** a regra **específica do serviço** (`catalogItemId` setado) vence a **regra padrão
  do profissional** (`catalogItemId = null`). Sem nenhuma regra aplicável ⇒ comissão **0** (a linha
  ainda é creditada ao profissional, com `commissionCents = 0`, p/ o relatório mostrar base sem
  comissão se o dono quiser).
- **Opt-in por conta** — sem regra cadastrada, o fechamento resolve profissional mas grava comissão 0;
  a seção/relatório de comissão só aparece pra quem tem profissionais (Onda C). Nada polui os ~50
  modelos de serviço puro sem profissional.

**Escopo (o que NÃO entra no v1):**
- **Comissão sobre desconto/gorjeta rateados por linha** — base é o bruto da linha.
- **Multi-profissional por comanda** (atribuição de linha a linha) — v1 é um profissional por comanda.
- **Fechamento de comissão / “vale” / pagamento ao profissional** — v1 só **calcula e relata**; o
  pagamento em si (marcar “pago ao profissional”) é follow-up (viraria um model `CommissionPayout`).
- **Faixas/metas (comissão progressiva por volume)** — regra é percentual OU fixo, linear.
- **Comissão de quem NÃO é `Professional`** (ex.: comissão do operador que lançou) — fora do escopo;
  o relatório por operador já existe (`revenueByOperator`).

```prisma
// null = regra PADRÃO do profissional (vale p/ qualquer item sem regra específica);

model CommissionRule {
  id             String       @id @default(cuid())
  accountId      String // User.id do dono (tenant)
  account        User         @relation("CommissionRuleAccount", fields: [accountId], references: [id], onDelete: Cascade)
  professionalId String
```

```ts
// src/lib/commission.ts — cálculo PURO de comissão (sem DB). Espelha a disciplina
// de orderTotalCents: número derivado de entradas inteiras, dinheiro em centavos.

export interface CommissionRuleLite {
  catalogItemId: string | null; // null = regra padrão do profissional
  percentBps: number | null; // pontos-base (4000 = 40,00%)
  fixedCents: number | null; // comissão fixa POR UNIDADE
}

/** Escolhe a regra aplicável a um item: a específica do serviço vence a padrão do
 * profissional (catalogItemId null). Sem regra aplicável → null. PURA. */
export function pickCommissionRule(
  rules: CommissionRuleLite[],
  catalogItemId: string | null,
): CommissionRuleLite | null {
  if (catalogItemId) {
    const specific = rules.find((r) => r.catalogItemId === catalogItemId);
    if (specific) return specific;
  }
  return rules.find((r) => r.catalogItemId === null) ?? null;
}

/** Comissão de uma linha (centavos). percentBps sobre o bruto (unit × qtd);
 * fixedCents POR UNIDADE (× qtd). Sem regra → 0. Nunca negativa. PURA. */
export function commissionForLine(opts: {
  unitPriceCents: number;
  quantity: number;
  rule: CommissionRuleLite | null;
}): number {
  const { rule } = opts;
  if (!rule) return 0;
  if (rule.percentBps != null) {
    const line = opts.unitPriceCents * opts.quantity;
    return Math.max(0, Math.round((line * rule.percentBps) / 10000));
  }
  if (rule.fixedCents != null) {
    return Math.max(0, rule.fixedCents * opts.quantity);
  }
  return 0;
}
```

## Riscos e notas

- **Comissão é snapshot, não derivada** — a decisão-âncora. Mudar a regra depois **não** mexe em
  comandas fechadas (igual `unitPriceCents`/`nameSnapshot`). O único ponto que recalcula é a
  **reabertura** (limpa o snapshot de propósito).
- **Atribuição de profissional é o ponto sutil** — v1 credita **um** profissional por comanda
  (explícito no fechamento **ou** o único do agendamento ligado). Comanda com **>1** agendamento de
  profissionais diferentes → sem crédito automático (o operador escolhe no fechamento, ou fica sem).
  Multi-profissional por linha é follow-up documentado. Isso evita adivinhação (mesmo princípio do
  `needsReview` com múltiplos agendamentos [[agenda-in-system-reminders]]).
- **Base = bruto da linha** — desconto/acréscimo/gorjeta de comanda ficam fora do cálculo no v1 (ratear
  por linha é ambíguo; gorjeta em geral é do profissional). O relatório mostra `baseCents` (Σ bruto) e
  `commissionCents` separados, então o dono vê a base de cálculo.
- **Percentual em pontos-base (`Int`)** — nunca float; a UI resolve `%` ↔ bps na borda, igual desconto
  resolve `%` → centavos ([[caixa-despesas-reposicionamento]]). `Math.round` a centavo.
- **Onda F compartilhada com a iniciativa 8** — respeitar o **append** no `onda-f.sql`; nunca duplicar
  manual × migration ([[prod-schema-drift-destravar]]). A ordem de execução das duas iniciativas não
  importa (tudo `IF NOT EXISTS`).
- **Custo da tx de fechamento** — a comissão adiciona 1 `findMany` de regras + 1 `update` por item
  dentro da tx crítica. Comandas típicas têm poucos itens; aceitável. Se virar gargalo, dá p/ trocar os
  N updates por um `$executeRaw` com `CASE`/`VALUES` — otimização, não requisito do v1.
- **Gate de dono** — regra e relatório de comissão são dados sensíveis (quanto cada um ganha): só
